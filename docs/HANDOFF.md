## How to run things
- **Scrape (stays up, retries by itself, restarts itself if work remains):**
  `gh workflow run crawl.yml -f total_jobs=20 -f procs=2 -f max_items=0 -f max_tenders=0 -f stagger=120 -f rescrape=false -f documents=true`
  (inputs also: `project=` to use another hub project, e.g. `eprocure-eval`). GitHub allows 20 concurrent jobs, so a running pass blocks
  any other. Cancel with `gh run cancel <id>`; a manual cancel stops the self-restart. After a cancel, put claimed windows back:
  `update queue set status='pending', claimed_by=null, claimed_at=null where project='eprocure-tenders' and status='claimed'`.
- **Backfill document lists for new tenders** is done in the crawler now; to redo for old ones run `scripts/ops/seed_sections_backfill.py`
  then `gh workflow run backfill.yml -f total_jobs=20 -f procs=4 -f threads=8` (about 25 min, no portal traffic).
- **Speed:** edit threads with the dashboard slider or `scripts/ops/set_threads.py`. Applied on the runners' next heartbeat (about 30 s).
- **Deploy the hub:** `cd ~/projects/scrape-hub && .venv/bin/python -m pytest tests -q`, then
  `sudo rsync -a --exclude .venv --exclude .git --exclude .devdata --exclude tests --exclude .pytest_cache --exclude web/reports ./ /opt/scrape-hub/`,
  `sudo chown -R scrapehub: /opt/scrape-hub/scrape_hub /opt/scrape-hub/web /opt/scrape-hub/client`, `sudo systemctl restart scrape-hub`.
  Runners install the client from the `main` branch of the hub repo, so push before dispatching. A restart gives a short 502; runners retry.
- **Check state quickly:** `scripts/ops/state.py`; watch rate and outages on `/explore`.

## Rules and gotchas (learned the hard way)
- **Process rule (your instruction):** observe, write it down in `docs/OBSERVATIONS.md`, optimise everything known, verify with a small
  capped test, then run. Never cancel a healthy run on a guess. Saved as a memory.
- **Don't wipe data** unless told; experiments use a separate project (`project=eprocure-eval`).
- The portal's **search app goes down for minutes at a time** (about 17 outages in 29 hours, 26% of the time). The front page keeps answering,
  so only the uptime probe tells the truth. Runners hold after 3 failed checks; `min_threads` keeps a minimum going.
- **A tender is real only if it has a title and covers.** The portal answers with "session expired" or "Stale Session" pages when
  degraded; both are detected now, and the hub's known-record and window-stored checks ignore captures without covers.
- **Refused documents are deterministic per document** (by publication month), not load-related. Retrying never helps.
- A run ends when every window was tried, unless work remains: now `claim_next` waits and the hub re-issues failed windows after 3 minutes
  (never while the portal is down), and the workflow restarts after the 5.5-hour cap.
- Captcha is not the bottleneck; portal latency under load is (about 3 s a request vs 0.5 s idle).
- Chromium crashes on this host (no browser tests here); file attachments from the session do not deliver, so charts go to `/reports/`.
- The user prefers short, direct updates with real numbers, wants things started when asked, and dislikes silence during long waits.
